# chinese-novelist-skill 借鉴分析

> 日期：2026-10-25
> 对象：https://github.com/PenglongHuang/chinese-novelist-skill （v2.3.1，MIT 协议）
> 结论先行：**他们的强项是"写作方法论资产"，我们的强项是"工程化管线"。值得借鉴的不是流程（我们已领先），而是 prompt 资产与几个巧妙机制。**

---

## 一、对方是什么

Claude Code Skill 形态的中文小说创作助手：Phase 0 初始化 → Phase 1 三层递进问答 → Phase 2 规划确认 → Phase 3 逐章创作（串行/子Agent并行/Teams 三种模式）→ Phase 4 自动校验修复。产物是 markdown 文件 + 一个 JSON 写作计划。**没有评估能力，没有 Web 界面，质量校验只有字数**。

架构定位与我们完全不同：他们是"一套精心设计的 prompt + 文件协议"，跑在 Agent 会话里；我们是"产品化的写作+评估工具箱"，跑在自有管线里。

## 二、值得借鉴的点（按优先级）

### P0 — 立即可做，prompt 级改动，成本≈0

**1. 动笔前上下文顺序（近因效应利用）** ⭐ 最妙的一处细节

> 原文（chapter-checklist.md 阶段A）："动笔前最后读到的必须是正文语态文字（上一章结尾 + 基准段落），不要让大纲表格和摘要成为动笔前的最后上下文。"

LLM 对上下文**末尾**内容最敏感——最后喂给它的是表格和要点，输出就带"表格味"；最后喂的是正文语态，输出就更像正文。我们 `chapter-generation-service.ts` 拼 prompt 时应检查各段落顺序，确保**最近章节原文（语态参照）放在 prompt 最末尾**，蓝图/状态等结构化信息前置。

**2. AI 味负面清单（确定性检查项）**

他们把"去 AI 味"拆成了可执行清单：删"璀璨/瑰丽"类堆砌形容词、抽象陈述改具体动作（"心中涌起复杂的情感"→动作/对话）、打破四字格律陈词滥调（心潮澎湃/热血沸腾）、长短句交替、口语化对话。v2.3.1 已做成"量化 AI 味检查"。

我们 `repetition.ts` 抓的是机械重复，但**AI 腔没人管**。落地方式二选一：
- 轻量：负面清单注入 `correct-rewrite.md` / revise 反馈；
- 重量：新增确定性检测器（高频 AI 词表命中率 + "不是…而是…"句式频率），作为 repetition 之后的第二道零成本 gate。

**3. 防注水扩充诊断表 → revise 反馈**

content-expansion.md 的精华是"扩充前先诊断"：场景太薄→感官肌理；跳跃太快→关键时刻放慢（子弹时间）；情感平面→内心展开；对话干瘪→层次丰富。配**防注水判据**："删掉这段扩充，故事是否变差？"以及五类无效扩充（风景堆砌/凑字回忆/重复已知/过渡冗长/对话注水）。

我们字数不足时 revise 反馈笼统。把诊断表写进 revise prompt，让模型先诊断再扩充，比"请扩写到 3000 字"有效得多。他们的稀薄版/充实版对照示例（悬疑现场/言情约会/奇幻异域三题材）是现成的 few-shot 素材，可直接吸收。

### P1 — 机制级新增，一周内量级

**4. 文风基准 + 本书校准段落（治跨章节文风漂移）**

`03-文风基准.md` 四件套：文风指纹（对话占比 35%-45%、短句为主、叙述距离等量化指标）+ 基准段落（2 段 500-800 字范例）+ AI 味负面清单 + **本书校准段落**（第 1 章定稿后提取开头钩子段+高张力段共 600-1000 字回填，作为全书文风锚点）。

我们的 bible 有风格设定，但没有"**可注入的正文级文风锚点**"。落地：第 1 章 pass 后自动（或让 reviewer 挑）提取 1-2 个最佳段落存 `writer.db`，后续每章生成时作为 few-shot 注入。对长篇后期文风漂移是对症药。这也正好补上我们 `writing-grammar.ts` 只有"规则"没有"范例"的缺口。

**5. 事实词典的"读者已知 / 计划揭示"两栏（信息不对称控制）**

他们大纲内嵌设定与事实词典：`名词/事实 | 首现章节 | 读者已知 | 完整真相 | 计划揭示`，配套硬规则：**先登记后动笔（禁止现场编数字）、到期必兑（弃用也要登记）、角色信息边界（他不知道的事不能说破）、自报数字核对（正文写"八个字"就得真数出八个字）**。

我们的 `state-update` 结构化程度其实更高（characters/facts/foreshadows/timeline 全是结构化 delta），但它是**事后记账**，缺两个前瞻维度：
- "读者已知"：同一事实的**读者视角信息边界**——反派真名第 8 章才揭，前 7 章角色对话就不能说破。我们的 facts 只有"世界真值"，没有"读者/角色可知值"。
- "计划揭示"：foreshadow 只有 open/resolve 生命周期，没有"计划第几章回收"。写长篇时伏笔悬空就是缺这个。

落地：StoryState 的 foreshadow 增加 `plannedResolvePosition?`，facts 增加 `revealedToReader: boolean`；生成时把"本章到期应回收的伏笔"作为强指令注入（我们已有 OPEN_FORESHADOWS 区块，升级为"到期伏笔必须回收"）。

**6. 钩子/开头技法库按题材注入**

十三种结尾钩子、十种开头技巧、章首引子七式，**全部带分题材示例**（悬疑/言情/奇幻/历史/科幻各一例）。我们的 `writing-grammar.ts` 已按平台分流（番茄/盐选/豆瓣），蓝图也有 ending_hook 字段，但正文 prompt 里只有"章末断点钩子"一句要求，模型只能自由发挥。

落地：把技法库整理成分题材素材，在蓝图阶段就让 LLM **选型**（本章用哪种钩子），正文阶段带对应示例。跟我们的 genreProfile/targetPlatform 概念天然契合。MIT 协议，素材可直接用（注明来源即可）。

### P2 — 大工程，规划级

**7. 并行章节生成的写入协议**

他们子 Agent 并行模式的四条协议值得整段抄录，如果我们未来做并行生成：
- 共享文件只许 Edit 字段级修改、**改前必须重读**、禁止脚本整体重写（绕过并发检测）；
- 每批只改自己章节的 status/wordCount 字段；
- 跨批次衔接：不阻塞等待，以大纲"承接上章/悬念钩子"栏为衔接依据，**全部完成后主 Agent 对接缝做衔接检查**（读前批末章结尾+后批首章开头，断裂处轻量修顺）。

注意：我们的 recentChapters 上下文机制在并行下会退化（后批看不到前批正文），他们的对策是"大纲驱动衔接 + 事后接缝修复"，等于承认了并行牺牲连贯性换速度。若做，适合先在"双引擎对比跑同章"这类场景试水。

**8. 章节摘要 300-500 字（衔接信息量）**

他们每章收尾追加 300-500 字摘要供连贯性参考；我们 state summary 是 50-150 字 + arcSummaries。150 字对"承接语态和情绪落点"可能不够。低成本试验：summary 放宽到 300 字，看 golden 集连贯性维度有无变化。

## 三、我们已领先、不必学的

| 维度 | 他们 | 我们 |
|------|------|------|
| 质量校验 | 仅字数脚本 + 3 轮重写 | 八维评分 + grade 门 + revise/block + evidence 追溯 |
| 防重复 | "桥段≤2次间隔≥3章"靠 LLM 自觉登记 | k-shingle + Jaccard 确定性算法 |
| 叙事状态 | 大纲内嵌表格，手工维护 | 结构化 StoryState delta + 版本化 + state-rebuild |
| 断点续写 | JSON status + Phase 0 检测 | SQLite + resume + Web 暂停/继续/取消 |
| 评估 | 无 | 五维 eval + HTML 报告 + 改稿对比 + golden 回归 |
| 平台适配 | 无概念 | 番茄/盐选/豆瓣/通用四套写作语法 |

三层递进问答、偏好记忆等交互设计面向 Claude Code 会话场景，对 CLI/Web 产品参考意义有限。

## 增补：v2.3.2 更新（2026-10-30 查证并取回）

> 上游 2026-10-29 发布 v2.3.2（14 commits）。本地参照已取回 `research/chinese-novelist-skill/`（v2.3.2 tag，外部克隆不入库，与 OpenMontage 同惯例）。查证来源：GitHub API commits/tags/compare + 克隆实测。

### 实质改动两条（其余为文档/工具链）

1. **章节摘要承接人物处境**（chapter-checklist 第 4 步）：写本章前除读 `00-人物档案.md` 外，须读 `99-章节摘要.md` 里上一章及出场人物的处境与后果——上游在补**状态承接**，即我们 StoryState 结构化 + 亲缘人名锁定已覆盖的事，它用手工摘要重新发明了一遍。
2. **机械配额 → 语境判断**（chapter-guide/chapter-checklist 大改）：
   - 删硬指标："每章 3000-5000 字硬性/至少 2 个张力波峰/对话≥30%/至少 1 个意外转折/前 20% 决定生死"
   - 改语境化："张力强度与章节用途匹配，**允许人物消化后果和关系沉淀**；不按固定字数插冲突；**不为套用技巧另造危机**；**不为制造意外临时加事**"
   - 去 AI 味从"词表替换"（删"璀璨"类）改为"**功能判断**：动作/对话已传达情绪就不再追加同义心理总结；不按词表机械替换；保留人物声音"
   - 工具链：字数脚本 Python→Node（scripts/check_chapter_wordcount.mjs）

### 判断：两条路在收敛（互相验证）

v2.3.2 的内核与我们 battle3→v4 的教训同构：battle3 的 v2 处方死于硬指标（情感闸门 85 卡死上沿、治逻辑治出"解谜机器"），v4 才学会"禁抽象标签但不禁内心"。上游从"规则硬化"往回撤，我们从"规则过矫"往回调——**两头在中间碰上了**。
