## 0. 顾问开篇：直面批评与定性判决

用户（兼具独立小说作者与全栈开发者双重身份）对当前 Web 端工作台给出了极具穿透力的严厉批评：**“生搬硬凑、没有产品思维”**。

作为产品架构顾问，在深入审阅全栈代码与当前运行状态后，我的结论是：**用户的批评百分之百切中要害。现有系统的本质是「把后端若干个 CLI 脚本、临时文件目录和数据库表，生硬地在前端导航条上拉了一排 Tab 进行图形化暴露」。**

### 0.1 为什么说“生搬硬凑、没有产品思维”？
在软件工程中，这种现象被称为**「康威定律反向泄漏（Conway's Law Leaked into UI）」**与**「工程实现细节直通界面（Implementation Leakage）」**：
1. **代码包（Package）等于导航栏**：`packages/writer` 变成了「项目列表」；`packages/eval` 变成了「质量评估」；`packages/eval` 的 audit 子模块变成了「逻辑审计」；`packages/audiobook` 变成了「有声书」；模型的环境变量变成了「模型配置」。五个平铺的顶部入口没有任何生命周期关联，用户在写书、看书、评书、转有声书之间反复跨跳，却找不到一条完整的工作流线。
2. **磁盘目录（Directory）等于业务实体**：`packages/web/server/routes/audiobook.ts` 直接扫描 `dist/` 下以 `audiobook` 开头的文件夹，把开发者在命令行里随意指定的临时目录名（`audiobook-v3`、`audiobook-v4`）直接剥离出 `v3`、`v4` 字符，作为「制作版本」摆在有声书首页的核心位置。这不仅让真实作者完全摸不着头脑，更让早已废弃的旧实验流程在界面上挥之不去。
3. **CLI 命令行参数（Argv）等于表单项**：`Audiobook.tsx` 中的构建表单塞满了 `project`, `chapters`, `group`, `engine`, `chars`, `epStart`, `coverRun`, `noVideo` 8 个原始技术参数，连书名都需要作者手动手打，甚至默认硬编码为 `'最后一班森铁'`。作者不是在操作一款创作工具，而是在给 `child_process.spawn()` 填写调用参数。
4. **数据孤岛（Siloed Data）导致心理断层**：小说母本保存在 `data/writer/writer.db`，评估产物在 `data/evals/` 和 `data/reports/`，逻辑审计存在内存与临时 JSON，有声书依赖外部配置文件 `data/audiobook/projects/<书名>.json` 与 `dist/` 静态文件。整套系统在底层数据和前端界面上，都没有**「一本书」**这个真正统领一切的最高产品实体。

### 0.2 2.0 终局定位拍板
用户的终极愿景提出：*“是不是要打造一个影视行业的创作台，自动化生成小说，从小说可以分发剧本，精简短篇故事，有声书创作，视频有声书创作，打造漫剧，或者 AI 短剧，把小说创作系列的衍生作品等等”*。

我的架构判决：
> **NovelEval 2.0 的定位必须坚决拍板为：个人作者的「小说 IP 一源多形态创作台」（IP Franchise Studio for Solo Creator）。**
> 
> - **我们要什么**：以「小说母本（Canon Novel）」为原点，基于结构化数据库与自研管线，向下游自动化分发并制作「有声书、视频有声书、精简短篇故事、分镜剧本、漫剧与短剧物料」的一站式内容工场。
> - **我们坚决不要什么**：
>   1. **不要做多人协作的影视协同 SaaS**：单人作者不需要通告单（Call Sheet）、剧组排期、多角色权限审批，加这些是严重的架构负资产；
>   2. **不要做重度时间线非编软件（如网页版剪映/Premiere）**：单人作者的核心生产力来自于 AI 管线的确定性自动化（Prompt 驱动、结构化分镜、自动对齐、两遍响度规一化），而非在浏览器里逐帧拖拽轨道路由；
>   3. **不要做公有制片大杂烩**：坚持本地优先（Local-First）、数据主权归作者所有、管线断点可续、物料一键出海/国内平台。

## 2. Q1 信息架构重构：从小说 IP 一源多形态衍生

针对作者“一源多形态影视创作台”的愿景，必须彻底重构系统的概念模型与信息架构。

### 2.1 核心五层实体模型（Core Domain Hierarchy）
我们建立以**「IP 母本（Book）」**为绝对核心的五层实体架构。每一层都有明确的用户心智定义，禁止任何后端技术名词向下泄漏：

```
Level 1: 【IP 母本 / 书】Book (Novel IP)
  │      用户心智："我在创作哪本作品？这本书的世界观、主角、设定是什么？"
  │
  ├─ Level 2A: 【母本创作与设定】Canon & Bible
  │      用户心智："故事的设定集(Bible)、大纲(Outline)与正文章节(Chapter)推进到哪了？"
  │
  ├─ Level 2B: 【质量保障门禁】Quality Gates (Audit & Eval)
  │      用户心智："这本书逻辑通不通？有没有战力崩坏或坑没填？文笔质量如何？"
  │
  └─ Level 2C: 【衍生作品族】Derivative Works (★ 2.0 核心枢纽)
         │  用户心智："我要把这本小说变成什么衍生形态？"
         │
         ├─ [形态 A] 视频有声书 (Video Audiobook)
         ├─ [形态 B] 精简短篇故事 (Condensed Short / Digest)
         ├─ [形态 C] 分镜影视剧本 (Screenplay / Script)
         ├─ [形态 D] 动态/静态漫剧 (Comic Drama)
         └─ [形态 E] AI 短剧物料包 (Micro-Drama Package)
                │
                └─ Level 3: 【交付单元 / 集】Unit / Episode
                       │  用户心智："这一集（或这一话、这一幕）讲了哪几章的故事？效果好不好？"
                       │
                       ├─ Level 4: 【制作执行流水线】Job Execution Pipeline
                       │      用户心智："当前任务执行到了哪一步（台本标注→TTS合成→装配→审听）？"
                       │
                       └─ Level 5: 【成品资产包】Deliverable Assets
                              用户心智："最终生成了哪些能发到平台的成片、字幕、文案、缩略图？"
```

#### 每一层实体的心智契约与禁语表
| 实体层级 | 业务术语 | 用户心智（User Mental Model） | 系统职责与数据源 | **严格禁止暴露的工程词汇** |
|:---|:---|:---|:---|:---|
| **L1** | **Book (书/IP)** | “我的这一部原创作品” | 聚合所有正文、设定集、质量报告与所有衍生作品；对应 `project` 唯一 ID | 禁止暴露 `dbPath`, `sqlite file`, `writer.db` |
| **L2** | **Work (衍生作品)** | “这本书的某一类商业成品线” | 承载该衍生形态的全局参数（音色班底、并章策略、分辨率、风格）；对应独立产物目录 | **坚决废除 `v3`, `v4`, `run`, `AUDIOBOOK_ROOTS`** |
| **L3** | **Episode (集/单元)** | “具体可消费的一集节目/一幕剧” | 绑定对应的若干母本章节（如 1-3 章），维护播放预览、审听报告、场景图、台本 | 禁止暴露 `epStart`, `group` 算子公式 |
| **L4** | **Job (生产任务)** | “系统正在干活的进度指示” | 负责异步调用底层 CLI、实时推流 SSE 日志、捕获异常并支持暂停/重试 | 默认折叠隐藏 `spawn argv`, `uvx`, `ffmpeg -filter_complex` |
| **L5** | **Asset (交付资产)** | “拿来就能发布到平台的成品” | 提供 MP4 视频、MP3 音频、SRT 字幕、封面图、YouTube/B站上传元数据下载 | 禁止暴露本地绝对路径（如 `/Users/.../dist/`） |

将现有的 5 个平铺顶栏彻底砍掉，重构为**三格顶栏**：
- **我的书架（Bookshelf）**：默认主页，汇聚所有正在创作的书籍；
- **任务中心（Jobs）**：全局异步任务抽屉（写作、生成、有声书渲染、全书审计等）；

## 3. Q2 有声书模块深度重构方案

### 3.1 彻底抹杀“v3/v4 制作版本”，实现内部缓存透明化
- **现状病灶**：在 `packages/web/server/routes/audiobook.ts` 中，系统将 `dist/audiobook-v3`、`dist/audiobook-v4` 作为平行版本展示，甚至在页面中要求用户切换版本胶囊。
- **重构准则**：
  1. **禁止 UI 出现任何 `v3` / `v4` / `run` 字眼**。
  2. **确立单一权威产物根（Canonical Asset Root）**：
     - 在文件系统层，重构输出路径规划为：`dist/derivatives/<bookId>/audiobook/`。
     - 每一集统一落盘在 `dist/derivatives/<bookId>/audiobook/episodes/ep<NN>/`。
     - 针对历史遗留资产（现存的 `dist/audiobook-v3` 和 `dist/audiobook-v4`），后端路由提供**透明资产聚合回退（Asset Fallback & Coalescing）**算法：
       ```ts
       // 伪代码：后端静默解析集资产，对前端只输出唯一的规范集对象
       function resolveEpisodeAsset(bookId: string, epNum: number) {
         // 1. 优先读取规范新路径
         const canonicalPath = join(DIST_ROOT, 'derivatives', bookId, 'audiobook', `ep${epNum}`);
         if (existsSync(canonicalPath)) return canonicalPath;
         
         // 2. 兼容历史遗留：优先取 v4（最新的音视频），图片若缺失则自动借用 v3 的 scenes
         const v4Path = join(DIST_ROOT, 'audiobook-v4', `ep${epNum}`);
         const v3Scenes = join(DIST_ROOT, 'audiobook-v3', `ep${epNum}`, 'scenes');
         return coalesceAssets(v4Path, v3Scenes);
       }
       ```
  3. **废弃的旧版本直接归档**：在后端扫描时，旧的、残缺的、无有效成品的目录标记为 `archived`，在前端默认过滤不显示，彻底消除用户的认知负担。

### 3.2 多书多集的空间定位与导航架构
针对用户痛点*“小说多了，一个小说十几集，十个小说一百个 item 平铺，怎么找？”*：

1. **层级下钻与空间收敛**：
   - 绝不允许在全局页面平铺 100 个集！
   - 导航路径严格收敛为：
     `我的书架 (10 本书卡片)` ➔ 点击《最后一班森铁》 ➔ `书工作台 (Tab: 衍生工场)` ➔ `有声书模块 (只展示该书的 15 个集)`。

   - 在有声书工场的顶部面包屑中，嵌入快速换书下拉菜单：`我的书架 > [《最后一班森铁》 ▾] > 有声书工场`，允许作者在不同小说的衍生作品间一秒切换，无需退回主页。

### 4.1 详细用户旅程（User Journey Walkthrough）

#### Step 1: 在书工作台激活衍生形态（Derivatives Hub）
- **页面位置**：`/books/:id/works`
- **用户交互**：作者写完小说前 10 章后，切换到「衍生工场」Tab。系统展示卡片阵列：
  - 【有声书与视频】（已就绪，状态：待启动）
  - 【精简短篇故事】（规划中）
  - 【分镜影视剧本】（规划中）
- **触发**：作者点击有声书卡片上的 `[开启有声书工程]`。
- **参数自动化**：系统后台自动以该书名在 `data/audiobook/projects/<书名>.json` 建立配置文件，自动从正文提取出主要出场人物（如程砚秋、周德厚、苏野），预分配默认音色方案，直接引导进入集概览墙。

#### Step 2: 极简一键制作与实时监控（Production & Job Stream）
- **页面位置**：`/books/:id/works/audiobook`
- **用户交互**：作者看到推荐卡片 `制作第 01 集 (第 1-3 章)`，直接点击主按钮 `[立即开始制作]`。
- **系统处理**：
  1. 页面不跳转，当前集卡片进入脉冲加载态（`[制作中: 台本标注 25%]`）；
  2. 底部轻量呼出 Job 控制台，以干净的进度条展示流水线阶段：`[1/4 规则标注] ➔ [2/4 语音合成] ➔ [3/4 音频装配] ➔ [4/4 视频渲染]`；
  3. 任务完成后，系统自动无缝衔接触发机器审听（`listen`），无需作者手动点击。

#### Step 3: 审听复核与“毫秒级精修”（Proof-Listening & Surgical Fix）
- **页面位置**：`/books/:id/works/audiobook/episodes/1`
- **用户交互**：制作完成后，卡片状态更新为 `[已就绪]` 或 `[需复核 (发现 1 处错读)]`。作者点击卡片进入单集详情。
- **系统处理**：
  1. 左侧播放器自动加载成片与字幕；
  2. 右侧「审听雷达」精确列出 CER > 0.3 的坏段（Bad）和缺失段（Missing）；
  3. 作者点击错读项，播放器自动 seek 到对应时间戳（如 `02:15`）；
  4. 作者确认是专有名词错读，直接在界面点击 `[加入发音纠错表]` 并输入正确读音；
  5. 点击 `[修复该段]`：后台仅删除该特定切片的音频缓存，重新调用 TTS 合成并无缝替换，3 秒内完成精修，彻底免除整集重新渲染的痛苦。

#### Step 4: 资产交付与平台发布（Export & Material Packaging）
- **页面位置**：`/books/:id/works/audiobook/episodes/1`（Tab: 上传物料）
- **用户交互**：作者点击 `[下载发布包]`，系统打包下载：
  - `EP01_最后一班森铁_1080p.mp4`（高清成片）
  - `EP01_最后一班森铁.srt`（精确对齐字幕）
  - `EP01_封面缩略图.jpg`
  - `YouTube_Upload_Meta.json`（自动填充符合平台政策的标签、简介与 AI 披露声明）

### 5.1 详细对标分析与官方文献

#### 1. CapCut / 剪映
- **参考来源**：[CapCut Video Editor Workflow Documentation](https://www.capcut.com/) & [Storyflow Analysis: Descript vs CapCut for Content Creators](https://storyflow.so/blog/descript-vs-capcut-for-content-creators)
- **IA 核心模式**：以「项目（Project）」为容器，内部由「时间线轨道（Tracks）」和「资产库（Assets）」组成。
- **交互哲学**：**“模板与效果预设永远先于参数”**。用户要加一个字幕特效或画中画，直接选“复古雪花”或“现代卡点”，背后的帧率、滤镜矩阵全部封装。
- **采纳决策**：NovelEval 现在的 `--snow`、`--cold-open`、`-vf scale=1920:1080` 绝不能以参数开关形式出现在第一屏，必须封装为「视频风格预设：年代雪夜怀旧风（默认含雪花与缓推）」和「纯音频解说风」。

#### 2. Descript
- **参考来源**：[Descript Help: Multi-track Sequences & Script Editing](https://help.descript.com/hc/en-us/articles/10324838634125-Multi-track-sequences-overview)
- **IA 核心模式**：`Drive ➔ Project ➔ Script Editor ➔ Sequences ➔ Export`。
- **交互哲学**：**“Script-First（文本即界面）”**。Descript 把复杂的音频波形编辑颠覆为“改文本就像改 Word”。在文本上改一个错别字，后台自动做 AI 重新语音合成（Overdub）。
- **采纳决策**：我们的集详情页（`AudiobookEpisode.tsx`）天然具备 `scripts` 与 `whisper` 数据。必须借鉴 Descript，让用户在台本 Tab 看到错读词时，直接在文本上点“更正并替换”，而不是去重新跑命令行。

#### 3. ElevenLabs Studio & Projects
- **参考来源**：[ElevenLabs Projects Documentation: Long-form Audio Creation](https://elevenlabs.io/docs/projects/overview)
- **IA 核心模式**：专门为长篇有声书（Audiobooks）设计的项目架构：`Project ➔ Chapters ➔ Paragraph Blocks`。
- **交互哲学**：**“角色音色绑定（Character Voice Sheet）与段落缓存”**。在书籍层一次性配置“老周头 = 深沉长者音”、“苏野 = 青年警官音”，全书所有章节自动生效；改动某一段文本，只有该段的 Block 会显示“Regenerate”，其余 Block 缓存永久保留。
- **采纳决策**：彻底落实 `data/audiobook/projects/<书名>.json` 作为书级配置中心，让作者在界面上可视配置角色音色；在界面上清晰标出哪些段落命中缓存，哪些段落重新合成。

#### 4. 喜马拉雅音剪 / 番茄创作平台（A+ 智能创作台）
- **参考来源**：[喜马拉雅音剪 AI 官方工场](https://xpy.ximalaya.com/) & [番茄小说创作者服务平台](https://fanqienovel.com/)
- **IA 核心模式**：网文有声化标准链路：`导入网文 ➔ AI 智能画本(旁白/对白识别) ➔ 角色配音 ➔ 音效配乐 ➔ 导出与发布`。
- **交互哲学**：四步式向导工作流。极其重视“画本准确率”与“多播配音”。
- **采纳决策**：当前我们的 `packages/audiobook/src/annotate.ts` 已经拥有优秀的规则与 LLM 标注能力。喜马拉雅的经验证明：作者非常关注“这句对白到底是谁说的”。我们应在单集详情中将台本标注归属可视化展示，并支持手动纠偏。

#### 5. StudioBinder
- **参考来源**：[StudioBinder Film Production Software Solutions](https://www.studiobinder.com/)
- **IA 核心模式**：以影视工程全阶段贯穿：`Pre-Production (Script/Storyboards) ➔ Production ➔ Post`。
- **交互哲学**：阶段化看板管理，严格的工序门禁（Script 锁定后才能进行 Storyboard 分镜设计）。
- **采纳决策**：借用其**阶段化门禁思想**——正文未定稿，不盲目跑全书有声；评估发现 P0 严重逻辑漏洞，提示作者先修复母本再衍生。同时坚决剔除其适合百人团队的排期表、通告单与预算报销体系。

#### 6. YouTube Studio
- **参考来源**：[YouTube Studio Content Management & Upload Flow](https://studio.youtube.com/)
- **IA 核心模式**：`Channel Dashboard ➔ Content ➔ Video Details ➔ Checks ➔ Visibility`。
- **交互哲学**：结构化元数据校验机制。针对 2025 年起强制实施的 AI 生成内容披露政策，YouTube 提供了严格的逐项自检（Altered or synthetic content disclosure）。
- **采纳决策**：我们的 `packages/audiobook/src/youtube.ts` 已经生成了 `youtube-upload.json` 和 `UPLOAD.md`。必须将其无缝呈现在集详情的“发布交付”面板中，形成带复选框的物料清单，让作者一键复制、无忧合规发布。

## 7. Q6 组件品质决策与设计系统轻量升级

用户抱怨*“有些表单组件是原生实现的，简陋，没有品质感”*。这引发了一个核心技术选型决策：
**我们是否要大动干戈引入一套庞大的组件库（如完整 AntD / MUI / 全量 shadcn + Tailwind）？**

### 7.1 技术选型权衡：决不为了“面子”过度工程

| 方案 | 优势 | 致命缺陷 | 顾问判决 |
|:---|:---|:---|:---|
| **方案 A：全量引入 Tailwind + shadcn/ui** | 业界流行，现代化视觉质感极强 | 需要全量重构现有 `styles.css`（1900 行）；引入复杂的 PostCSS 构建链与巨量 node_modules；对单人本地工具有严重的维护过载风险 | **否决**（过度工程） |
| **方案 B：引入重量级 Ant Design / Mantine** | 组件极全，开箱即用 | 视觉风格浓重“后台管理系统”味（ERP 感），与小说/影视创作的沉浸暗黑艺术质感完全背离；样式覆盖极痛苦 | **否决**（气质不符） |
| **方案 C（拍板）：Radix UI 无样式原语 + 现有 Design Tokens 封装** | 1. 极轻量，按需引入；<br>2. 彻底解决原生 select/dialog/checkbox 的交互缺陷；<br>3. 完美继承现有的 1900 行 CSS 变量体系与暗黑主题；<br>4. 零破坏性迁移。 | 需要写极少量的样式映射类（仅针对 5 个高频控件） | **★ 唯一拍板采纳** |

### 7.2 实施规范：高频控件封装清单
我们只需针对最让用户感到简陋的 5 个原生控件进行 Radix UI 替换封装：

1. **`UiSelect`（基于 `@radix-ui/react-select`）**：
   - 彻底消灭原生的 `<select>`；
   - 支持丝滑的下拉浮层动画、键盘上下键导航、选中勾选态、禁用态；
   - 完美适配 `--input-bg`, `--border-hover`, `--card` 等主题变量。
2. **`UiSwitch`（基于 `@radix-ui/react-switch`）**：
   - 替换丑陋的原生 `input[type="checkbox"]`；
   - 具有现代平滑滑动动效的胶囊开关，用于“跳过视频”、“自动审听”等二值操作。
3. **`UiDialog`（基于 `@radix-ui/react-dialog`）**：
   - 替换生硬的弹出框与浏览器原生 `alert/confirm`；
   - 带毛玻璃遮罩（Backdrop Blur）、ESC 一键关闭、焦点锁定的优雅模态窗口。
4. **`UiTabs`（基于 `@radix-ui/react-tabs`）**：
   - 用于书工作台的 Tab 切换（正文 / 质量 / 衍生工场），自带底部平滑游标高亮。
5. **`UiToast`（基于 `@radix-ui/react-toast`）**：
   - 用于异步任务完成、发音表更新成功的非阻塞右下角轻量提示。

### 7.3 品质感的真正来源：排版与微文案哲学
**软件的品质感 80% 来自于信息层级与交互微文案，只有 20% 来自于组件库边角。**
- **原则一：每屏只有一个醒目的 Primary 按钮**（例如「立即制作第 05 集」）；其他辅助操作全部使用次级幽灵按钮（Ghost/Outline）；
- **原则二：严禁向用户说技术切口，必须说创作人话**：
  - ❌ *“请填写 chapters 参数（如 1-15），并设置 group 并章数”*
  - ✅ *“将把第 4、5、6 章合并制作成 1 集有声书，预计时长 15 分钟”*
- **原则三：空态必须带有明确的行动下一步**：
  - ❌ *“该版本还没有集。点右上构建新集”*
  - ✅ *“本书尚未生成任何有声节目。正文已写就 15 章，建议 [一键开始制作第 01 集] 试听品质。”*

### 8.2 M0 五大不可动摇的验收标准（Acceptance Criteria）

在 M0 改造完成后，必须通过以下五项严苛验收，缺一不可：

1. **顶栏绝对纯净**：新用户在全站任何页面的顶栏，**绝对看不到**孤立的“有声书”、“质量评估”、“逻辑审计”入口，所有衍生与质检操作均从具体的“书”内发起；
2. **三步触达制作且零手打**：从书架点击任意一本书进入，3 次点击以内必须到达「开始制作第 N 集」的确定性按钮，且**全程不需要手动键盘输入一次书名或章节数字**；
3. **彻底绝迹 v3/v4**：全站所有页面的 DOM 节点和文本展示中，**零处出现** `v3`、`v4` 或 `制作版本` 字样；
4. **意图卡替代参数墙**：构建新集区域必须默认呈现清晰的中文人话说明（*“制作第 N 集 · 包含第 A–B 章 · 豆包配音班底”*），而不是 8 个原始技术输入框；
5. **死开关百分之百修复**：在单集审听中勾选 fix 或 srt，网络请求 Payload 必须真实携带对应参数，CLI 执行命令必须产生对应的 `--fix` / `--srt` 行为。

## 9. 顾问总结与施工禁令（Anti-Patterns）

NovelEval 已经具备了极其惊艳的底层资产：从大纲推演、逐章写作、质量把控，到角色标注、两遍响度规一化装配、Whisper 机器审听回验。
**你手里拿的原本是一台精密跑车的各个核心引擎部件，只是之前不小心把它们装成了一个布满裸露电线的控制电箱。**

在迈向 2.0 阶段，请团队牢记以下**七大施工禁令**：
1. **禁令一**：严禁在顶部导航栏再增加任何新的平级业务入口（剧本、漫剧、短剧一律下沉进书内衍生）；
2. **禁令二**：严禁在前端向用户暴露底层文件目录名（如 `dist/`、`audiobook-v*`）；
3. **禁令三**：严禁把 CLI 的原始参数（如 `--chars`、`--ep-start`、`--no-snow`）直接作为主界面的表单项；
4. **禁令四**：严禁在有声书代码中硬编码任何特定小说书名；
5. **禁令五**：严禁脱离具体的“书”去要求作者上传独立 TXT 文本跑评估；
6. **禁令六**：严禁在现阶段写任何重度网页视频时间线编辑器（坚决依赖自动化管线）；
7. **禁令七**：严禁在 M0 阶段去动 `writer.db` 的数据库 Schema（仅通过 Web 路由与聚合适配层即可完美实现所有 M0 体验重塑）。

保持克制，聚焦作品，把工具深埋在创作流程之下。这是 NovelEval 2.0 从“脚本拼盘”真正蜕变为“IP 衍生创作台”的必由之路。
